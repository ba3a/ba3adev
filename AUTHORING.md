# Authoring

A short, practical guide to writing for ba3a.dev (English: projects, project docs, devlog) and my.ba3a.dev (Russian: personal blog). Publishing is a `git push` to `main`. The engine, coffer, has a page per feature in [the coffer docs](https://github.com/ba3a/coffer/blob/v0.1.0/docs/README.md); this file links there instead of repeating it. Operations and go-live are in [OPERATIONS.md](OPERATIONS.md) (the go-live and operations runbook).

## Set up a new computer

1. Install Node 24 (`.nvmrc` says `24`; nvm reads it, other installers just need version 24 or newer) and git.
2. Clone the repository.
3. Create `.env.local` from the example and fill in the three values. This is the one setup step that cannot be in the repository:

   Copy `.env.local.example` to `.env.local` and set:

   ```
   CLOUDFLARE_ACCOUNT_ID=...
   R2_ACCESS_KEY_ID=...
   R2_SECRET_ACCESS_KEY=...
   ```

   The first value is the Cloudflare account that owns the private R2 bucket `ba3a-media`; the other two are an R2 token with Object Read & Write on that bucket. `.env.local` is ignored by git; never commit it. `CLOUDFLARE_API_TOKEN` in the example file is only for the one-off Cloudflare setup script and is not needed to write.
4. Run `npm install`. Its `prepare` script (`scripts/prepare.mjs`) installs the git hooks (`coffer hooks install`) and downloads every original photo the lock file lists (`coffer media pull`), so you get the complete working copy.

A second computer can download the originals only after the first `git push` from the working copy that holds them (the push uploads them to R2); before that the bucket is empty and the download prints a notice.

Without credentials, `npm install` still works: the hooks are installed, the download is skipped, and one notice says which variables are missing and what to run later (`npx coffer media pull`). With `CI` set (as on GitHub Actions) the script does nothing; the deploy workflow pulls the originals itself. Hooks need Node on the `PATH` of git, so start git from a terminal if a graphical client does not find it.

To check the setup, run `npm test`. It builds both sites, so it needs a network (it clones the public `roto` and `specloop` repositories), JDK 21 (the roto API reference is generated by Gradle and Dokka, which download their own parts on the first run) and the seed photos (restored by the test itself if the checkout lacks them). The whole run takes around 2 minutes. For a quick check of your own work use `npm run build` and `npm run check`.

## Preview

```sh
npm run dev
```

builds both sites with drafts and scheduled posts (each carries a banner) and serves them with live reload: ba3a.dev on `http://localhost:4000/`, my.ba3a.dev on the next port (4001). The terminal prints the addresses. A build error never stops the watcher; the browser shows the problems and reloads when you fix them. Details: [Authoring](https://github.com/ba3a/coffer/blob/v0.1.0/docs/authoring.md). Analytics are never part of a preview.

To build like production, run `npm run build` (output in `dist/`) and then `npm run check`. Add `-- --drafts` to `npm run build` to include drafts.

## A new post

```sh
npm run new -- devlog "Why I put a loop around Claude Code"
npm run new -- blog "Шкатулка из сосны"
```

The first argument is the blog id: `devlog` on ba3a.dev, `blog` on my.ba3a.dev (not the site name; `my.ba3a.dev/blog` also works). The command creates `content/ba3a.dev/devlog/{slug}/index.md` or `content/my.ba3a.dev/{slug}/index.md` as a draft. The slug comes from the title (Cyrillic is transliterated: `shkatulka-iz-sosny`); change the folder name before publishing if you want another address. Options: `--date 2026-12-01T09:00`, `--tags "tools/coffer, release"`, `--slug name`. An existing post is never overwritten.

Write the text under the front matter, drop pictures next to `index.md`, and remove `draft: true` to publish.

## Front matter

```markdown
---
title: A walk in the hills
date: 2026-12-01 09:00
tags: [hiking/alps, photography]
summary: Two days, one tent.
cover: cover.jpg
series: alps
seriesPosition: 1
draft: false
aliases: [alps-walk]
projects: [coffer]
---
```

Only `title` and `date` are required. Dates are read in the site's time zone (Europe/Samara for both sites). The other keys are `location`, `camera`, `images`, `tracks` and `map` (see below), and unknown keys are ignored. Every key is described in [Posts](https://github.com/ba3a/coffer/blob/v0.1.0/docs/posts.md#front-matter).

## Images

Put the originals next to the post and refer to them by file name, with alt text and an optional caption:

```markdown
![A pine board on the bench.](bench.jpg "The board before marking out.")
```

- The text in brackets is the alt text; a missing one is a warning. The quoted text is the caption.
- JPEG, PNG, WebP and HEIC (iPhone) files work as they are; GIF and SVG do not. The build makes the small versions and never publishes the original. See [Images](https://github.com/ba3a/coffer/blob/v0.1.0/docs/images.md).
- A cover is a file name in `cover:`; without one, the site generates a card with the title.
- One picture can have its own privacy policy through the `images` key (see [Location policy](#location-policy)).

How originals are kept: photos are not stored in git. They live in the private R2 bucket and are listed, by content hash, in `media.lock.json`, which is in git. The patterns are `media.include` in `coffer.yaml`: raster images (`jpg`, `jpeg`, `png`, `heic`, `heif`, `webp`) and videos (`mp4`, `webm`) anywhere below `content/ba3a.dev/devlog/` and `content/my.ba3a.dev/`. Project pictures (cards, logos, key art) under `content/ba3a.dev/projects/` and SVG files stay ordinary git files. The hooks do the work:

- `git commit` refreshes `media.lock.json` and stages it;
- `git push` uploads what R2 lacks, and aborts the push if it cannot (no credentials, no network), so nobody ever gets a lock whose photos are not stored;
- `git checkout`, `git pull` and merges download new originals.

By hand, `npx coffer media status` shows differences and `npx coffer media lock`, `push` and `pull` do each step. Full reference: [Media originals](https://github.com/ba3a/coffer/blob/v0.1.0/docs/media.md).

## Carousels

```markdown
:::carousel[Three steps of the assembly]
![Dry fit, no glue.](box-1.jpg "Dry fit.")

![Checking the corners with a square.](box-2.jpg "Square check.")
:::
```

The words in brackets name the carousel for screen readers. A carousel holds only images. See [Carousels](https://github.com/ba3a/coffer/blob/v0.1.0/docs/carousels.md); a working example is in `content/my.ba3a.dev/pervyj/index.md`.

## Maps and GPX

Put one or more `.gpx` files in the post folder. Every GPX file there is a track: it is published for download and drawn on the post's map, together with the photos that have a published position. Choose or title tracks with the `tracks` key, or turn the map off:

```markdown
---
title: Ridge walk
date: 2026-12-01
tracks:
  - { file: day-two.gpx, title: Day two }
map: false
---
```

A track always carries exact positions, so a post with a GPX file is listed in the exact-locations report. Remove the file or list only the files to publish to keep a recording private. See [Maps and GPX tracks](https://github.com/ba3a/coffer/blob/v0.1.0/docs/maps.md).

## Location policy

By default the build strips the GPS position and the camera data from every published photo (`location: { default: strip, camera: strip }` for both sites in `coffer.yaml`). More permissive values are explicit choices, from the least to the most specific: a tag in `tags.yaml`, the post, one image.

```yaml
# content/my.ba3a.dev/tags.yaml
hiking:
  location: keep
```

```markdown
---
title: A day in the valley
date: 2026-12-01
location: coarse
images:
  IMG_1043.jpg:
    location: strip
---
```

`location` is `strip`, `coarse` (about a kilometre) or `keep` (exact); `camera` is `strip` or `keep`. A tag setting covers its whole subtree. When a post has several tags that give different values, the strictest wins, but a tag without a `location` entry has no opinion. So a post tagged both `hiking` (keep) and `woodworking/boxes` (no entry) publishes exact GPS positions. Check the tags of every hiking post.

Every build prints the posts that publish exact locations (and stores them in `.coffer/report.json` under `exactLocations`); the deploy workflow shows the list in the job summary of a successful run. Read it before you push. Rules and examples: [Location policy](https://github.com/ba3a/coffer/blob/v0.1.0/docs/location-policy.md).

## Tags

Tags are slash paths: `woodworking/boxes`. Using a tag in a published post creates its page, and a tag page lists its subtree. Names and descriptions go in `tags.yaml` beside the posts of a blog; without an entry a tag is shown by its last segment.

```yaml
woodworking/boxes:
  name: Шкатулки
  description: Небольшие коробки с крышками и петлями.
```

An entry for a tag no published post uses is a warning. See [Tags](https://github.com/ba3a/coffer/blob/v0.1.0/docs/tags.md).

## Series

Name the series in the front matter. The number is optional and only a sort key; without it parts are in date order. Number all the parts or none: numbered parts always come before unnumbered ones.

```markdown
---
title: The second part
date: 2026-12-08
series: pervye-shkatulki
seriesPosition: 2
---
```

Posts get "part n of m" navigation computed at build time; earlier posts are never edited. A name and description go in `series.yaml` beside the posts:

```yaml
pervye-shkatulki:
  name: Первые шкатулки
```

See [Series](https://github.com/ba3a/coffer/blob/v0.1.0/docs/series.md).

## Project tags and project blocks

Each project in `content/ba3a.dev/projects/{slug}/project.yaml` has a `tag` (for example `tag: specloop`). A devlog post is about the project when one of its tags equals that tag or lies below it, or when its front matter lists the project:

```markdown
---
title: Replanning in specloop
date: 2026-12-01
tags: [specloop/release]
projects: [roto]
---
```

Such a post gets a badge, a project block at its end (pitch, links, docs, the latest other posts) and a place in the project's feed. A slug in `projects:` that no project has fails the build. Link to a project from text with `[roto](project:roto)`. See [Posts about a project](https://github.com/ba3a/coffer/blob/v0.1.0/docs/projects.md#posts-about-a-project).

## Drafts and scheduling

- `draft: true` keeps a post out of the published sites. `npm run new` creates drafts.
- A post is published when it is not a draft and its date is not in the future. To schedule one, remove `draft: true` and set a future `date`, then push.
- The Refresh workflow checks about every 15 minutes whether a scheduled post is due, and then builds and deploys. GitHub starts scheduled runs late, so a post appears about 20 to 30 minutes after its date; project documentation changes appear within an hour. Scheduled workflows run only on the default branch (`main`).
- A draft or not-yet-due post is not resolved by a normal build, so a missing image or broken link in it is found on the day it becomes due. Run `npm run dev` or `npm run build -- --drafts` before you schedule it, and make sure its images are pushed.

See [Posts](https://github.com/ba3a/coffer/blob/v0.1.0/docs/posts.md#which-posts-are-published) and [Scheduled rebuilds](https://github.com/ba3a/coffer/blob/v0.1.0/docs/scheduling.md).

## Old slugs

Renaming a post folder changes its address. List the old slug and visitors are redirected permanently:

```markdown
---
title: A walk in the hills
date: 2026-12-01
aliases: [alps-walk, hills-trip]
---
```

Details: [URLs](https://github.com/ba3a/coffer/blob/v0.1.0/docs/urls.md).

## Writing on the phone

The GitHub web editor (or app) works for text. Create `content/my.ba3a.dev/{slug}/index.md` (or `content/ba3a.dev/devlog/{slug}/index.md`) with the front matter above, because `npm run new` is not available there. Rules:

- Keep `draft: true` while you write, and do not refer to images yet. A draft is not published, and its images and links are not checked, but the build still reads its front matter. A typo in the `---` block (an invalid `date`, a tag with a space or other forbidden character, a missing `title`) fails the whole build and nothing is deployed, so a draft is not safe to commit blindly. Copy the block from an existing post, keep `title` and a real `date`, and write tags from letters, digits, `.`, `_` and `-`, separated by `/`.
- If the Deploy workflow turns red after a commit from the phone, open the failed run (see "What fails the build"), fix the front matter in the web editor and commit again. The live sites stay as they were.
- Add the photos later from a computer: put them next to `index.md` (the hooks upload them on push), add the Markdown for them, and remove `draft: true`.
- If you publish a post that refers to an image that is not in the repository (the lock file and R2 do not have it), the build fails with `file:line:column missing image 'name.jpg'`. Nothing is deployed and the live sites stay as they were. Fix the post or add the image and push again.

## What fails the build

Errors stop the build, and nothing is deployed:

- broken front matter (also in a draft), an invalid tag or series name, a slug used twice, an unknown project in `projects:`;
- a broken link, an anchor that does not exist, a missing or undecodable image, a bad GPX file, an invalid `coffer.yaml` or `project.yaml`;
- a project documentation source that cannot be fetched or a reference command that fails;
- in `coffer check` (the deploy runs it after the build): missing preview metadata, a bad feed or sitemap, and published images that carry data the policy forbids.

Warnings do not fail the build, but fix them: an image without alt text, an entry in `tags.yaml` or `series.yaml` that no post uses, an unused key in `images:`, and undocumented symbols in a generated API reference.

Where to read them: locally, `npm run build` prints each error as `file:line:column message`. Every build also writes `.coffer/report.json` (`errors`, `warnings`, `exactLocations`, `info`), which is not deployed. In GitHub, open the failed run of the Deploy workflow: the log of the failed step lists the errors. After a successful build the job summary prints the warnings and the exact-locations list from the report (`scripts/build-summary.mjs`). See [Links, images and the build report](https://github.com/ba3a/coffer/blob/v0.1.0/docs/links.md) and [Checking a finished build](https://github.com/ba3a/coffer/blob/v0.1.0/docs/checks.md).

## Adding a new tool project

Use this checklist for a project with documentation pulled from its own repository, as roto and specloop do (see their `project.yaml` files).

1. The project repository is public. No token, webhook or deploy key is added to it; this repository polls it anonymously.
2. Create `content/ba3a.dev/projects/{slug}/` (the folder name is the slug) with `project.yaml`, `index.md` (text only, no front matter) and the card picture.
3. Declare the project:

   ```yaml
   # content/ba3a.dev/projects/lathe/project.yaml
   name: lathe
   pitch: One line that says what the tool does.
   kind: tool
   status: in-development
   card: card.png
   cardAlt: A short description of the card picture.
   featured: true
   order: 5
   tag: lathe
   license: Apache-2.0
   repo: https://github.com/ba3a/lathe
   docs:
     source:
       git: https://github.com/ba3a/lathe.git
       ref: main
     guides:
       - dir: docs
         order: [getting-started.md]
   ```

   The required keys are `name`, `pitch`, `kind`, `status`, `card` and (for a tool) `repo`. `docs.source` is a `git` address with a `ref`, or a `path` to a folder. `guides` lists the folders of Markdown files and the files that come first. A `docs` block with neither guides nor a `reference` publishes nothing and writes no link.
4. Optional: a `reference` generated from the source, with a `command`, `format` (`html` or `json`), `output` and `title`, and optionally `index` (`dokka`, so that guides can link to symbols with `ref:Name`) and `undocumented` (a pattern that turns missing-documentation lines of the command output into warnings). The roto reference runs Gradle and Dokka, so it needs JDK 21 on the machine and in CI (the deploy workflow installs it). A reference command runs code from the repository, so configure it only for repositories you trust. The roto and specloop files show both kinds.
5. The card (and any logo or key art) goes in the project folder as a regular git file; PNGs below `content/ba3a.dev/projects/` are not covered by the media store.
6. Register nothing else. The Refresh workflow reads this configuration (`coffer rebuild-needed` asks `git ls-remote` for every git source), so a push to the project repository is picked up within the hour. A folder source (`path`) is not polled; it is deployed by a push to this repository.
7. Run `npm run dev` and check `/made/{slug}/` and `/made/{slug}/docs/`, then `npm run build` and `npm run check`.

References: [Projects](https://github.com/ba3a/coffer/blob/v0.1.0/docs/projects.md), [Where a project's documentation comes from](https://github.com/ba3a/coffer/blob/v0.1.0/docs/docs-sources.md), [Project documentation](https://github.com/ba3a/coffer/blob/v0.1.0/docs/project-docs.md).

## A landing page

A tool can have a landing page instead of a README-style page. specloop and coffer do: the `index.md` of each is the text of its page, and the theme turns it into the designed sections. Every other tool page is unchanged.

The text is ordinary Markdown with two conventions:

- **Sections.** Each section starts with an empty marker, `<div class="section-marker" id="name"></div>`. The `id` is the name of the section and becomes the `id` of the section on the page, so `#name` links work. A page without markers is a normal tool page. The names the layout knows are `hero`, `problem`, `audience`, `how-it-works`, `timeline`, `spec-example`, `features`, `compare`, `dogfood`, `quick-start`, `faq` and `final-cta`; a page uses the ones it needs (specloop has ten, coffer twelve). The sections with two columns, and what their visual is, are set per project in the `layouts` table of `themes/ba3a/templates/partials/landing.njk`. (A comment such as `<!-- section: hero -->` would be dropped by the Markdown renderer, which is why the marker is an element.)
- **Eyebrows.** A `######` heading right before the `##` heading of a section (before the `#` of the hero) is the small label above it. It is published as a paragraph, not as a heading.

How each part of the Markdown is shown (a table as three cards, a list as a timeline, a quote as a chat, `###` questions as an accordion, and so on) is in `themes/ba3a/templates/partials/landing.njk`. The look is `themes/ba3a/assets/landing.css`, loaded by landing pages only. All words on the page come from `index.md`; the few words the layout adds are in `themes/ba3a/i18n/en.yaml`, under `landing.{slug}`. A new landing page needs an entry in the `layouts` table, its strings, a `landing-{slug}` palette in `landing.css` if its accent differs, and its own test. The brand pictures of the project (`logo.svg`, `logo-dark.svg`, `favicon.svg`, `favicon.ico`, `apple-touch-icon.png`) are in `themes/ba3a/assets/{slug}/`; the card picture is the preview image of the page.

## If the scheduled workflow stops

GitHub disables scheduled workflows of a public repository after 60 days without activity, and Refresh is what publishes scheduled posts and picks up project docs. The Keepalive workflow and a job inside Refresh try to prevent it (see `scripts/keepalive.mjs`), but a real commit is the only sure way to restart the 60-day clock. If GitHub disabled Refresh anyway, a commit does not turn it back on: enable it by hand. Open the Actions tab, choose Refresh, then "Enable workflow" (or run `gh workflow enable refresh.yml`). Make a real commit afterwards so that it does not happen again. A workflow disabled by hand is left alone by the keepalive. More in [OPERATIONS.md](OPERATIONS.md#things-to-know) (the go-live and operations runbook).

## Analytics

Analytics are not configured: neither site in `coffer.yaml` has an `analytics` key, so no page loads a third-party script. The engine supports the Cloudflare Web Analytics beacon (cookie-free, no consent banner), and the content security policy in `deploy/_headers` already allows it. To turn it on, add this to a site in `coffer.yaml` (the token is not a secret: it is the public site identifier, which you get in the Cloudflare dashboard under Web Analytics by adding the site, and no secret is needed in this repository):

```yaml
analytics:
  provider: cloudflare
  token: "0123456789abcdef0123456789abcdef"
```

The beacon is part of production builds only, never of `npm run dev`. Ad blockers remove it, so counts are approximate. For script-free numbers, the traffic analytics of the Cloudflare zone count requests on the server side. See [Analytics](https://github.com/ba3a/coffer/blob/v0.1.0/docs/analytics.md).
